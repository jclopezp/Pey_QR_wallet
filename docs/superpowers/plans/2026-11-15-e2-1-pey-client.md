# E2-1 Pey client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One typed Pey client in the API, selectable as mock or live, that creates QRs and bank accounts without leaking the API key.

**Architecture:** `PeyClient` is the only surface other stories call. `HttpPeyClient` speaks `https://api.pey.mx` with Node `fetch`, zod, a 10 s timeout, and no automatic retry. `MockPeyClient` never touches the network. `createPeyClient` picks one from `PEY_MODE` and refuses to boot live mode without `PEY_API_KEY`. Pey payload types stay inside `apps/api/src/integrations/pey`. Error codes the web translates live in `packages/shared`.

**Tech Stack:** Node `fetch`, zod, Vitest (from E1-1). No new HTTP library and no new test dependency.

**Spec:** `_docs/Project/stories/E2-1-pey-client.md`. Wire shapes are taken from Pey OpenAPI `2026-10-20` (`https://docs.pey.mx/openapi.json`), which replaces the ticket's "propuesto, revisar" field names.

## Global Constraints

- Call Pey only from `apps/api`. The web app and `packages/shared` must not import `integrations/pey`.
- API key and webhook secret stay in `.env`. Never log them, return them, or prefix them with `VITE_`.
- Base URL `https://api.pey.mx`. Auth header `Authorization: Bearer <PEY_API_KEY>`.
- Create QR is `POST /codi/qr`. Do not send `generateImage: true`. Do not call `generateImage` as a feature.
- Always send `metadata` `{ qrId, businessId }` as strings.
- There is no Pey test environment. Tests must not call `api.pey.mx`.
- TypeScript `strict`. No `any` without a comment. Validate Pey responses with zod.
- Amounts in our domain are integer cents. Pey's `amount` is a JSON number in MXN.
- Ask before adding a dependency. This plan adds none.
- Do not commit `.env`.

## Decisions locked from the OpenAPI spec

Pey `POST /codi/qr` body fields we send: `amount` (number, MXN, `0` lets the payer type it), `concept` only when present, `bankAccountId` (string ULID), `metadata` (scalar values only). Response `201`: `{ id, qrString }`. Our name for `id` is `peyQrId`.

Pey `POST /bank-account` body: `{ alias, name, clabe, entity }` with `entity` of `PERSON` or `BUSINESS`. Response `200`: `{ id, codiStatus }` where `codiStatus` is `PENDING | PROCESSING | ACTIVE | ERROR`.

Pey `GET /bank-account/{id}` returns the account, including the full CLABE and `codiStatus`. The client may parse `clabe`. Callers in E1-9 must not persist it. This client must not log it.

Pey errors are `{ error: { message, type, requestId } }`. `error.message` can echo request data. Our `PeyError.message` is always our code, never Pey's message.

Map HTTP status to our code: `401` and `403` → `pey_unauthorized`; `408`, network failure, abort, `503` → `pey_unavailable`; `400` → `pey_invalid_request`; anything else including `500` and a 2xx body that fails zod → `pey_unknown`. Keep Pey's `error.type` on `PeyError.peyType` when it is a short token (`INVALID_CLABE`, `SERVICE_UNAVAILABLE`, …). Drop it if it contains the API key or a CLABE.

Timeout is `10_000` ms via `AbortSignal.timeout`. One attempt for every method in this story, including reads. No retry loop.

`PEY_MODE` is `mock` or `live`. Missing or any other value fails startup. Default in `.env.example` is `mock`. `PEY_BASE_URL` defaults to `https://api.pey.mx`.

## Review Focus

- A 401 body that contains the API key must produce `pey_unauthorized` whose message and `peyType` do not contain the key. Covered in Task 3.
- A hung `POST /codi/qr` must send exactly one request and then `pey_unavailable`. Covered in Task 3.
- `amountCents` `1` must be JSON `0.01`, and `15050` must be JSON `150.5`, not a binary-float expansion. Covered in Task 1.
- `createQr` must omit `generateImage` and omit `concept` when the caller passes none. Covered in Task 2.
- `createBankAccount` logs must not contain the CLABE or the Authorization value. Covered in Task 4.
